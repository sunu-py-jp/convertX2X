非同期HTTP

受け付け・状態確認・結果取得

ファイルを送ってジョブIDを受け取り、完了後に結果をダウンロードします。HTTP受付も直接Queue依頼も、同じ状態確認APIと結果取得APIを使えます。

利用条件と処理の流れ

  1. 管理者が CONVERSION_STORAGE_CONNECTION_STRING とQueueトリガーの派生設定を用意する。
  2. POST /api/jobs でファイルを登録する。
  3. 返された statusUrl を Retry-After に従って確認する。
  4. succeeded になったら resultUrl を取得する。

すべてのAPIはFunction認証です。Azure上で複数のAPIへ同じキーを使う場合は、x-functions-key にFunction AppのHostキーを渡します。Storageのキーとは別の認証です。

非同期が未設定なら、このページの全APIは 503 ASYNC_DISABLED を返します。追加の入出力Storage登録だけでは有効になりません。有効化の設定を参照してください。

POST /api/jobs — ジョブを登録する

POST/api/jobs

本文にPPTX・PPT・PDFの生バイト列を送り、Content-Type: application/octet-stream を指定します。filename・format・page・width は同期HTTPと同じクエリです。

受付時に容量・オプション・基本シグネチャを検査し、入力Blobと初期状態を保存してからQueueへ送ります。文書構造やページ数の詳細な検査・描画はワーカーが行うため、202は変換成功の保証ではありません。

BASE_URL='https://YOUR_FUNCTION_APP.azurewebsites.net'
FUNCTION_KEY='YOUR_FUNCTION_KEY'

curl --fail-with-body \
  -H "x-functions-key: $FUNCTION_KEY" \
  -H 'Content-Type: application/octet-stream' \
  --data-binary @slides.pptx \
  "$BASE_URL/api/jobs?filename=slides.pptx" \
  --dump-header job-headers.txt \
  --output job.json

成功時は 202 Accepted、Location に状態確認先、Retry-After: 3 を返します。JSONの statusUrl も同じ確認先です。

{
  "job": {
    "id": "f6603efc-2fa8-4466-8d09-6d7c3ed94c18",
    "status": "queued",
    "filename": "slides.pptx",
    "options": { "width": null, "format": "png", "page": null },
    "createdAt": "2026-09-13T00:00:00Z",
    "updatedAt": "2026-09-13T00:00:00Z",
    "pageCount": null,
    "errorCode": null,
    "errorMessage": null
  },
  "statusUrl": "/api/jobs/f6603efc-2fa8-4466-8d09-6d7c3ed94c18"
}

ジョブIDはサーバーがUUIDとして採番します。HTTPから指定した出力コンテナーや output.mode を渡す機能はありません。保存先や個別画像保存を指定する場合は直接Queueを使います。

同じPOSTをもう一度送ると新しいジョブになります。レスポンス受領に失敗しただけで既存ジョブが取り消されることはありません。入力保存とQueue送信は単一トランザクションではなく、送信エラー時に入力や状態が残る場合があります。

GET /api/jobs/{id} — 状態を確認する

GET/api/jobs/{id}

id はハイフン付きUUIDです。既存ジョブなら200とJSON、Retry-After: 3 を返します。statusUrl や resultUrl は同一ホストの相対パスで、設定したルート接頭辞を引き継ぎます。

JOB_ID='f6603efc-2fa8-4466-8d09-6d7c3ed94c18'

curl --fail-with-body \
  -H "x-functions-key: $FUNCTION_KEY" \
  "$BASE_URL/api/jobs/$JOB_ID"
job.status意味呼び出し側の次の操作
queued受付済み待って状態を再取得
running処理中、または一時エラー後の再試行待ち待って状態を再取得
succeeded結果の保存が完了resultUrl からダウンロード
failed変換失敗、または再試行上限に到達errorCode・errorMessage を確認

状態の進み方は通常 queued → running → succeeded / failed です。ポーリング間隔によって途中の状態を観測できないことがあります。ページごとの進捗率や残り時間は返しません。

job の項目内容
id / statusジョブのUUIDと状態
filename / options正規化した入力名と、width・format・page
createdAt / updatedAtUTCのISO 8601日時
pageCount成功時の出力画像枚数。1ページ指定なら1。成功前は null。
errorCode / errorMessage失敗時のコードと説明。通常は null。

成功したレスポンスは、上記の job と statusUrl に resultUrl が加わります。失敗状態を確認した場合でも、状態API自体のHTTPステータスは200です。

{
  "job": {
    "id": "f6603efc-2fa8-4466-8d09-6d7c3ed94c18",
    "status": "succeeded",
    "filename": "slides.pptx",
    "options": { "width": null, "format": "png", "page": null },
    "createdAt": "2026-09-13T00:00:00Z",
    "updatedAt": "2026-09-13T00:00:08Z",
    "pageCount": 3,
    "errorCode": null,
    "errorMessage": null
  },
  "statusUrl": "/api/jobs/f6603efc-2fa8-4466-8d09-6d7c3ed94c18",
  "resultUrl": "/api/jobs/f6603efc-2fa8-4466-8d09-6d7c3ed94c18/result"
}

例の日時は形式説明用です。処理時間の目安ではありません。状態APIは内部のBlob保存先や接続情報を返しません。

GET /api/jobs/{id}/result — 結果を取得する

GET/api/jobs/{id}/result

成功状態が指す保存済みの結果を返します。このGETが変換をやり直したり、新しいZIPを作ったりすることはありません。

登録時の条件200の本文Content-Type
HTTP受付、またはQueueの zip／全ページ画像をまとめたZIPapplication/zip
HTTP受付、またはQueueの zip／1ページ指定画像1枚image/png / image/jpeg
直接Queueの imagesmanifest.jsonapplication/json

どの結果にも Content-Disposition: attachment、X-Page-Count、Cache-Control: no-store、X-Content-Type-Options: nosniff が付きます。

# HTTPで全ページを登録したジョブの結果
curl --fail-with-body \
  -H "x-functions-key: $FUNCTION_KEY" \
  "$BASE_URL/api/jobs/$JOB_ID/result" \
  --dump-header result-headers.txt \
  --output slides.zip

個別画像モードの結果は画像ではなくJSONです。 manifest内のStorage登録名・コンテナー・Blob名を使い、出力Storageの読み取り権限で画像を取得します。この機能に /images/{name} や /archive のHTTP APIはありません。manifestの形式を確認してください。

状態・結果取得でのエラー

条件応答
UUIDの形式が不正400 INVALID_JOB_ID
状態が見つからない404 JOB_NOT_FOUND
結果取得時に未完了、または失敗済み409 JOB_NOT_READY
非同期機能が無効503 ASYNC_DISABLED、Retry-After: 3

直接Queueの登録直後は、ワーカーが状態をまだ作成しておらず404になる場合があります。しばらく待って再確認してください。HTTP受付で返されたジョブは、Queue送信より前に初期状態を保存しています。

キャンセル・削除・Webhook通知のAPIはありません。Playgroundで待機を停止しても、受付済みの処理は継続します。再試行と保持期間についてはQueueの運用を参照してください。
