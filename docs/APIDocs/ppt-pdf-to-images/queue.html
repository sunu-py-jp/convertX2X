Azure Storage Queue

入力BlobとJSONで直接依頼する

元ファイルをBlobへ保存し、Queueへ入出力先を送ります。HTTPアップロードAPIやPlayground、初期状態Blobの事前作成は必要ありません。

送信側が行うこと

  1. 新しいUUIDを決め、PPTX・PPT・PDFを一意の入力Blob名へアップロードする。
  2. 制御用StorageのQueue conversion-jobs へ、次のversion付きJSONを送信する。
  3. ワーカーが作成する状態を確認し、成功した試行の結果を取得する。

入力・出力が別アカウントでも、Queueと状態Blobは CONVERSION_STORAGE_CONNECTION_STRING の制御用Storageに置きます。ファイル本体やBase64化した文書データをQueueへ含めません。

依頼JSON

次は、既定のStorageで全ページを個別PNGへ保存する例です。UUID、入力パス、コンテナー名は依頼ごとに用意します。

{
  "version": 1,
  "jobId": "f6603efc-2fa8-4466-8d09-6d7c3ed94c18",
  "input": {
    "storage": "default",
    "container": "documents-incoming",
    "blobName": "incoming/f6603efc-2fa8-4466-8d09-6d7c3ed94c18/slides.pptx"
  },
  "output": {
    "storage": "default",
    "container": "images-created",
    "prefix": "exports/slides",
    "mode": "images"
  },
  "filename": "slides.pptx",
  "options": {
    "format": "png",
    "width": null,
    "page": null
  }
}
フィールド必須・既定値意味
version必須、整数 1文字列の "1" は不可
jobId必須通常のハイフン付きUUID。正規化後は小文字。
input / output必須、オブジェクト以下の入出力指定を格納
input.storage / output.storage省略・nullなら default管理者が登録したStorage名。入力・出力の登録は別々。
input.container必須アップロード済み入力のコンテナー
input.blobName必須入力Blobの名前。最大1024文字。
output.container必須保存先。存在しなければ非公開で作成。
output.prefix省略・nullなら空文字保存パスの接頭辞。正規化後で最大512文字。
output.mode省略・nullなら zipzip または images。小文字で指定。
filename任意省略・空白時は入力Blobの末尾名。正規化した末尾名は最大255文字。
options任意省略なら自動寸法・全ページ・PNG。指定するときはオブジェクト。
options.format省略・nullなら pngpng / jpeg。前後空白を除去し、小文字に正規化。
options.width省略・nullなら自動1以上の32ビット整数。画像幅のpx指定。
options.page省略・nullなら全ページ1以上の32ビット整数。元文書の1始まりページ番号。

options: null は受け付けません。既定値を使う場合は options 自体を省略するか {} にします。内部の width・page・format はnullを指定できます。

JSONの検証とBase64

  • デコード後のJSONはUTF-8で最大48 KiB。UUIDだけのメッセージには対応しません。
  • 未知のフィールド、重複キー、末尾の追加JSON、不正な型、整数の文字列化は拒否します。
  • コンテナー名は3〜63文字の小文字英数字・単独ハイフン。先頭末尾は英数字で、連続ハイフンは不可です。
  • Blob名とprefixには制御文字、. / .. のパス区間を指定できません。prefixは前後空白と末尾の / を除いて正規化します。
  • 接続文字列・キー・SAS・任意URLを指定するフィールドはありません。Blob名は登録Storage内の名前として扱い、URLを取得する指示にはなりません。

Queueクライアントに QueueMessageEncoding.BASE64 を設定し、JSON文字列をそのまま渡します。FunctionsホストはBase64をデコードしてワーカーへ渡します。事前に自分でBase64化して、SDKでもう一度エンコードしないでください。

// Java送信側。接続設定は環境変数から取得する。
QueueClient queue = new QueueClientBuilder()
    .connectionString(System.getenv("CONVERSION_STORAGE_CONNECTION_STRING"))
    .queueName("conversion-jobs")
    .messageEncoding(QueueMessageEncoding.BASE64)
    .buildClient();

queue.sendMessage(json); // jsonはUTF-8の依頼JSON文字列

入力アップロードも行う実行例は QueueProducer.java にあります。元の直接Queue手順に、クラスパスと必要な認証設定を記載しています。

保存モード

output.modeoptions.page 省略options.page 指定
zip（既定）全画像を含むZIPを1つ保存画像1枚を保存。ZIPにはしない。
images各画像とmanifestを保存元の番号を保った画像1枚とmanifestを保存

images は画像を1枚ずつ保存し、一覧用のメタデータだけを蓄積します。入力文書の解析は1回です。全画像とmanifestの合計に出力サイズ上限が適用されます。

入力・状態・結果の保存場所

対象保存先
Queue制御用Storageの conversion-jobs
直接Queueの入力input.storage / input.container / input.blobName
HTTP受付の入力制御用コンテナー conversion-jobs の {jobId}/input
状態制御用コンテナー conversion-jobs の {jobId}/status.json
結果output.storage / output.container の {prefix}/{jobId}/results/{attemptUUID}/{出力名}

空のprefixには先頭の {prefix}/ が付きません。HTTP受付の出力は制御用コンテナー conversion-jobs、prefixなしです。attemptUUID はワーカーが試行ごとに生成します。

状態Blobは job・request・result を持ちます。request は正規化後の依頼です。成功状態の result は次の形で、実際の保存先を取得するための情報です。

{
  "storage": "default",
  "container": "images-created",
  "blobName": "exports/slides/{jobId}/results/{attemptUUID}/slides.zip",
  "contentType": "application/zip",
  "filename": "slides.zip",
  "pageCount": 3
}

上のパスは構造の説明です。実データの result.storage・container・blobName を使ってください。状態APIはこの内部レコードを直接返さず、ジョブと取得用の相対URLを返します。

個別画像のmanifest

images モードでは、状態の result が manifest.json を指します。GET /api/jobs/{id}/result でも同じJSONを取得できます。2ページ目だけを指定した場合の形式例です。

{
  "version": 1,
  "jobId": "f6603efc-2fa8-4466-8d09-6d7c3ed94c18",
  "mode": "images",
  "pageCount": 1,
  "images": [
    {
      "page": 2,
      "storage": "default",
      "container": "images-created",
      "blobName": "exports/slides/{jobId}/results/{attemptUUID}/page-0002.png",
      "contentType": "image/png",
      "filename": "page-0002.png",
      "sizeBytes": 12345
    }
  ]
}

page は元のページ番号、pageCount は出力画像の枚数、sizeBytes はその画像の実バイト数です。各画像の storage は依頼の output.storage と同じです。JPEGの画像名は page-0002.jpeg となります。

各画像は、manifestに記載されたBlobから読み取り権限を使って取得します。画像配信用のHTTPエンドポイントや、manifestからZIPを作るHTTPエンドポイントはありません。

{prefix}/{jobId}/results/{attemptUUID}/
  page-0001.png
  page-0002.png
  manifest.json

別Storageの登録

Functionsの環境変数役割JSONの指定例
CONVERSION_STORAGE_CONNECTION_STRING制御用と既定の入出力"storage": "default"
CONVERSION_INPUT_STORAGE_SOURCE追加の入力用接続input.storage: "source"
CONVERSION_OUTPUT_STORAGE_ARCHIVE追加の出力用接続output.storage: "archive"

JSONの登録名は [a-z][a-z0-9_]{0,31}、環境変数の接尾辞はその大文字表記です。default は予約名です。入力専用の登録は出力へ流用できず、逆も同様です。

登録はアカウント単位で、コンテナー単位の許可リストではありません。登録名の役割分離はStorage自体の権限を狭めません。入力の読み取り、出力の書き込み・コンテナー作成、結果APIを使う場合は出力の読み取り権限を、実際の接続にも付与します。

重複配送・再試行・保持期間

  • 同じID・同じ正規化済み依頼で成功済み／失敗済みなら、変換を繰り返しません。異なる依頼で同じIDを使っても既存状態・結果を上書きしません。
  • 新しい変換や失敗後の条件変更には新しいUUIDを使い、入力Blobも一意にします。処理完了まで入力を上書き・削除しないでください。
  • 更新するBlobリースで同じジョブを排他制御し、試行ごとのパスと条件付き保存で古い試行の上書きを防ぎます。全画像・manifestの保存が終わった試行だけを成功として公開します。
  • 不正文書、上限超過、未登録Storage、入力なしは失敗状態になります。Storage障害や変換の競合は再試行します。
  • ホスト設定は maxDequeueCount=10、失敗後の visibilityTimeout=1分。上限後は conversion-jobs-poison で失敗状態にします。
  • 不正JSONや不正UUIDなど、ワーカーが有効な依頼を解析できない場合は状態Blobを作れません。直接投入直後の404と区別し、長時間見つからない場合はワーカーとログを確認します。

単一ワーカーでも厳密なFIFO順序や、変換処理の実行が常に1回だけになることは保証しません。入力のETag検査は読み取り中の差し替えを防ぐもので、再試行間の入力更新を許可するものではありません。

入力・状態・結果・途中で失敗した試行のBlobは自動削除しません。保持期間とライフサイクル管理を運用側で決めます。新規コンテナーは非公開で作成し、既存コンテナーの公開設定は変更しません。
