直接Queue連携

外部システムから、アップロード済みOfficeファイルのBlob参照だけをQueueへ送信します。

外部システムから直接依頼する

HTTPでジョブを登録せず、OfficeファイルをBlobへ保存し、制御Storageの office2md-jobs QueueへJSONを送ります。ワーカーが状態を作成し、同期HTTPと同じ変換処理を呼びます。状態Blobを送信側で作成する必要はありません。

  1. 新しいUUIDと、そのUUIDを含む入力Blobパスを決める。
  2. ファイルをBlobへアップロードして完了を確認する。
  3. 次のJSONをBase64で1回だけエンコードしてQueueへ送る。
  4. 状態を確認し、成功状態が指す成果物だけを取得する。

QueueメッセージのJSON

{
  "version": 1,
  "jobId": "fc2e587d-9369-4a90-8b03-815589d5d4a3",
  "input": {
    "storage": "source",
    "container": "office-inputs",
    "blobName": "requests/fc2e587d-9369-4a90-8b03-815589d5d4a3/sample.docx"
  },
  "output": {
    "storage": "archive",
    "container": "markdown-results",
    "prefix": "converted"
  },
  "filename": "sample.docx"
}

この例は入力用source・出力用archiveの登録が必要です。同じStorageを使う場合は各storageを省略します。Storage登録を参照してください。

フィールド必須・既定値制約
version必須1 の整数。文字列や小数は不可
jobId必須ハイフン付きUUID。大文字は小文字へ正規化
input必須オブジェクト
input.storage省略/null: default入力用の登録名
input.container必須入力コンテナー
input.blobName必須既存Blob名。1,024文字以内
output必須オブジェクト
output.storage省略/null: default出力用の登録名
output.container必須出力コンテナー。なければ非公開で作成
output.prefix省略/null: 空文字512文字以内。前後の空白と末尾の / を正規化
filename省略/null/空白: 入力Blob末尾名パス部分を除き制御文字を置換。255文字以内、対応拡張子が必要

コンテナー名は3〜63文字の小文字英数字とハイフンで、先頭・末尾は英数字、連続ハイフン不可です。Blob名とprefixに制御文字や . / .. のパス区間は指定できません。登録名は [a-z][a-z0-9_]{0,31} で、空文字は既定名にならず不正です。

JSON本体はUTF-8で48 KiB以下です。未知フィールド・重複キー・余分なJSON・型の暗黙変換は拒否します。options、output.mode、接続文字列、SAS、任意URL、ファイル本体を入れる契約はありません。

Base64は1回だけ

ホストの messageEncoding は base64 です。Java SDKを使う場合はエンコード設定を有効にし、sendMessageにはJSON文字列をそのまま渡します。

QueueClient queue = new QueueClientBuilder()
    .connectionString(controlStorageConnection)
    .queueName("office2md-jobs")
    .messageEncoding(QueueMessageEncoding.BASE64)
    .buildClient();
queue.sendMessage(requestJson);

このコードは設定例の抜粋です。JSONを手動でBase64化してからSDKでもエンコードすると二重になり、処理できません。実行可能な送信例は QueueProducer.java、準備と実行手順は 元の直接Queueガイドを参照してください。

Storageと認証の境界

用途設定・使用場所
制御StorageCONVERSION_STORAGE_CONNECTION_STRING。Queueと状態Blobの保存先
既定の入力・出力storage: "default"。制御Storageを利用
別Storageの入力CONVERSION_INPUT_STORAGE_SOURCE に接続文字列を登録し、input.storage: "source"
別Storageの出力CONVERSION_OUTPUT_STORAGE_ARCHIVE に接続文字列を登録し、output.storage: "archive"

入力と出力の登録は別々です。出力専用に登録したStorageを入力として指定できません。環境変数の接尾辞は大文字、JSONの登録名は小文字です。DEFAULTは追加登録できません。登録名はアプリの参照先制限であり、アカウントキーそのものの権限を細分化するものではありません。

送信側には入力Blobの書き込みとQueueへの送信権限、ワーカーには入力Blobの読み取りと制御Storageの状態・Queue操作権限が必要です。出力側はコンテナー作成・Blob書き込みに加えて、HTTP結果取得・ZIP化用の読み取り権限も必要です。接続設定は設定ページを参照してください。

状態と成果物の保存先

制御Storage / office2md-jobs コンテナー
└── {jobId}/status.json

出力Storage / {output.container}
└── {output.prefix}/{jobId}/results/{attemptId}/
    ├── document.md
    ├── report.json
    └── images/...

prefixが空なら、その区間を省きます。attemptIdは試行ごとのUUIDです。保存先を推測してBlob一覧から集めず、成功状態のresult.artifactsを正として取得します。全ファイルを保存できた試行だけを公開し、ZIPは保存しません。

job:     id, status, filename, createdAt, updatedAt,
         sectionCount, warningCount, errorCode, errorMessage
request: 正規化した投入リクエスト
result:  storage, container, sectionCount, warningCount,
         artifacts: [{path, blobName, contentType, sizeBytes, eTag}, ...]

これはStorage内の状態レコードです。job.status == "succeeded" になったら、result.storage・containerと各artifact.blobNameを使います。初回処理前はstatus.jsonが存在しない場合があるため、404だけで即失敗と判断しません。

HTTPからも結果を取得できる

直接Queueで作られたジョブも、GET /api/jobs/{id}と成果物APIを使えます。返される resultUrl / reportUrl / archiveUrl / assetsBaseUrl への各HTTPリクエストに、x-functions-key ヘッダーでFunction Appのホストキーを渡します。HTTP状態APIには内部のBlob保存先を公開しません。Storageの資格情報とFunctionsの認証キーは別物です。

再送・競合・失敗

状況扱い
同じID・正規化後に同じ依頼同一ジョブとして処理。成功済み・失敗済みの終端状態を維持
同じIDで入力や保存先を変更JOB_ID_CONFLICT。元のジョブを上書きしない
変換不能・上限超過等ジョブをfailedにして理由を記録
一時的な処理・StorageエラーQueueで再試行。上限後は office2md-jobs-poison へ
構文が壊れたJSON等ジョブを特定できず状態を作れない場合がある

新しい変換ではjobIdと入力Blobパスを両方変えてください。投入後の入力を上書きすると、再試行が別の内容を読む可能性があります。入力のETag検査は1回のダウンロード中の変更を防ぐもので、再試行全体での不変性を代替しません。

入力アップロード後にQueue送信が失敗した場合は、元の入力を保持したまま同じJSONを再送します。完成成果物も変更しないでください。リースで同じジョブの配送を直列化しますが、全ジョブのFIFO順序やアプリ全体の同時実行1は保証しません。失敗試行を含むBlobの保持・清掃は運用側で決めます。

Version 2：入力版・付加情報・結果通知

既存のversion 1は引き続き使えます。以下の拡張はversion 2でのみ受け付けます。接続先の資格情報やURLをQueueメッセージに含めません。

{
  "version": 2,
  "jobId": "b6812181-8d03-4cb0-841a-225798074cf9",
  "input": {
    "storage": "source",
    "container": "documents-incoming",
    "blobName": "originals/book.xlsx",
    "expectedETag": "\"0x8EXAMPLE\""
  },
  "output": {
    "storage": "archive",
    "container": "converted-results",
    "prefix": "exports"
  },
  "metadata": {
    "documentId": "document-123",
    "revision": "7"
  },
  "notification": {
    "queue": "completed"
  }
}

input.expectedETagで原本の版を固定し、不一致はINPUT_VERSION_MISMATCHです。metadataは最大16項目の文字列マップ（キー64文字・値512文字・合計8KiB以下）、notification.queueは登録済み結果Queueのエイリアスです。metadataは認可情報ではありません。

Officeの成果物にはMarkdown・report・画像一式と、それらの参照・サイズ・SHA-256を持つManifestがあります。通知には大量の画像一覧を埋め込まず、確定した成果物の参照を返します。

通知はeventId・jobId・終端のstatus・入力版・metadata・結果参照・固定エラーを含みます。受信側でeventIdによる重複排除と最新revisionの照合を行ってください。通知失敗は送信待ちから再送し、変換はやり直しません。

結果と状態の保持期間は既定では無期限です。保持設定を有効にすると、アプリが所有するファイルだけを清掃します。清掃済みの結果取得は410 JOB_RESULT_EXPIREDです。状態を削除した後は同じjobIdの重複判定も終了します。

設定・権限・Private Endpoint・保持運用は共通の配置・運用手順、詳細な契約は直接Queueガイドを参照してください。未登録の入力・出力・通知先は使用できません。
