Movie → AAC

外部システムから直接Queueへ依頼する

動画をBlobへ保存し、Queueには入出力の参照をJSONで送ります。HTTP受付・Playgroundを経由せず、他システムから同じAAC抽出処理を実行できます。

送信側の手順

  1. 新しいUUIDを作り、AAC音声を含む動画を一意な入力Blobへ保存する。
  2. 制御用Storageの movie2audio-jobs Queueへ、version付きJSONをBase64で1回だけエンコードして送る。
  3. 状態API、または制御用Blobの状態を確認し、成功した試行のaudio.m4aを取得する。

CONVERSION_STORAGE_CONNECTION_STRING を設定した場合だけワーカーを登録します。Queueと状態Blobは制御用Storageに置き、入出力は同じStorageまたは事前に登録した別Storageを指定できます。ファイル本体・SAS URL・接続文字列・キーをQueueへ入れません。

依頼JSON

{
  "version": 1,
  "jobId": "f6603efc-2fa8-4466-8d09-6d7c3ed94c18",
  "input": {
    "storage": "default",
    "container": "videos-incoming",
    "blobName": "incoming/f6603efc-2fa8-4466-8d09-6d7c3ed94c18/meeting.mp4"
  },
  "output": {
    "storage": "default",
    "container": "audio-created",
    "prefix": "exports/meetings"
  },
  "filename": "meeting.mp4"
}
フィールド仕様
version必須。整数1
jobId必須。通常のハイフン付きUUID
input / output必須。以下の指定を持つオブジェクト
input.storage / output.storage事前登録したStorage名。省略・null時はdefault
input.container入力コンテナー
input.blobNameアップロード済みの動画Blob名
output.containerM4A保存先。未作成なら非公開で作成
output.prefix任意の保存先接頭辞。省略・null時は空
filename任意の入力表示名。省略・null・空白時は入力Blobの末尾名。正規化後は最大255文字。出力名はaudio.m4a固定

出力形式・音声選択・ビットレートの options やZIPモードはありません。最初のAACトラックをそのままM4Aにします。既定StorageのJSONと別StorageのJSONを利用できます。

JSON検証とBase64

Base64デコード後のJSONは正しいUTF-8で最大48KiBです。未知のキー・重複キー・末尾の追加JSON・不正な型は拒否します。UUIDだけの旧式メッセージは受け付けません。動画本体をBase64化して含める形式でもありません。

コンテナー名は3〜63文字の小文字英数字・単独ハイフンで先頭末尾は英数字です。Blob名は最大1024文字、prefixは前後空白と末尾スラッシュの正規化後で最大512文字です。制御文字・. / .. 区間・バックスラッシュ・?・#・:// を拒否します。登録Storage内のBlob名を指定する仕組みで、任意URLを取得する指示にはなりません。

Node.jsの @azure/storage-queue では、送信前にJSONをBase64化します。別のSDKでBase64自動エンコードを有効にした場合は、未エンコードのJSON文字列を渡してください。二重にエンコードしないでください。

import { QueueClient } from '@azure/storage-queue';
import { readFile } from 'node:fs/promises';

const queue = new QueueClient(
  process.env.CONVERSION_STORAGE_CONNECTION_STRING,
  'movie2audio-jobs'
);
const json = await readFile('queue-request.json', 'utf8');
await queue.sendMessage(Buffer.from(json, 'utf8').toString('base64'));

同梱の QueueProducer.mjs で動画アップロードとQueue投入を実行できます。入力アップロード・権限・運用の手順は直接Queueの開発者ガイドを参照してください。送信元にはBlobへ入力を保存する権限とQueueへメッセージを追加する権限が必要です。

別Storageの登録

環境変数役割JSON
CONVERSION_STORAGE_CONNECTION_STRING制御用と既定の入出力storage: "default"
CONVERSION_INPUT_STORAGE_SOURCE追加の入力用接続input.storage: "source"
CONVERSION_OUTPUT_STORAGE_ARCHIVE追加の出力用接続output.storage: "archive"

登録名は [a-z][a-z0-9_]{0,31}、環境変数の接尾辞は大文字です。default は予約名です。入力・出力の登録は別で、入力用登録を出力用としては利用できません。接続設定はサーバー側に置き、Queueでは登録名だけを渡します。

登録はアカウント単位で、コンテナーの許可リストではありません。接続が持つ実際の権限も、入力の読み取り、出力の保存・コンテナー作成に合わせて設定してください。結果APIを使う場合、出力側には読み取り権限も必要です。Queueへの投入権限は、この登録範囲へ処理を依頼できる権限として扱います。

登録Storageの接続設定を使うこの経路では、同期SAS保存用の CONVERSION_OUTPUT_ALLOWED_HOSTS は使いません。APIごとの役割を分け、呼び出し元が任意の接続先を追加できない形にしています。

入力・状態・音声の保存場所

対象保存先
入力input.storage / input.container / input.blobName
状態制御用Storageのmovie2audio-jobsコンテナー、{jobId}/status.json
出力output.storage / output.container / {prefix}/{jobId}/results/{attemptUUID}/audio.m4a

空のprefixなら先頭の {prefix}/ は付きません。ワーカーが試行ごとに attemptUUID を生成し、成功した試行だけを状態の result として公開します。パスを推測せず、状態に保存された情報を使ってください。

状態Blobは job・request・result を持ちます。request は正規化済みの依頼で、result は成功時に次のような記録を持ちます。

{
  "storage": "default",
  "container": "audio-created",
  "blobName": "exports/meetings/f6603efc-2fa8-4466-8d09-6d7c3ed94c18/results/8a21634b-dcb8-445c-b30e-aa615169aa4a/audio.m4a",
  "contentType": "audio/mp4",
  "filename": "audio.m4a",
  "sizeBytes": 9323,
  "etag": "\"0x8DD123456789ABC\""
}

HTTP状態APIは内部のrequest/resultやStorage参照を返さず、ジョブと取得用URLだけを返します。結果APIからM4Aを受け取るか、内部resultを使って自分のStorage読み取り権限でBlobを取得します。

重複配送・再試行・保持

  • 同じID・同じ正規化済み依頼が成功済み／失敗済みなら変換を繰り返しません。同じIDで異なる依頼を送っても既存状態や結果を上書きしません。
  • 状態Blobの更新可能なリースでジョブを排他制御します。途中で止まった処理は後続の試行へ引き継げます。変換処理が常に1回だけ実行されるという保証ではありません。
  • 入力Blobは依頼ごとに一意にし、処理完了まで上書き・削除しないでください。新たな変換や条件を変更した再実行には新しいUUIDを使います。
  • 不正動画・AAC以外・上限超過・未登録Storageなどは失敗状態になります。Storageの一時障害や実行枠の競合は再試行します。
  • maxDequeueCount=10、失敗時の visibilityTimeout=1分。上限後は movie2audio-jobs-poison で失敗状態にします。
  • 不正JSON・不正UUIDなど依頼を解析できない場合は、対応する状態Blobを作れません。直接投入直後の404と区別し、継続する404はQueue・ワーカー・poisonの状態を確認します。

Queueは厳密なFIFOではありません。プロセス内は同期とQueue合わせて1件、水平スケール時は複数インスタンスが並列に動作します。実行枠の数とアプリ全体の最大インスタンス数は別の設定です。

入力・状態・結果・未完了の試行のBlobは自動削除しません。保持期間とライフサイクル管理を運用側で決めます。新しいコンテナーは非公開で作成し、既存コンテナーの公開設定は変更しません。
